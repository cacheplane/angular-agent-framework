**Date:** 2026-08-31
**Goal:** Convert the neutral `Agent` contract's portability claim from belief into measurement.

## Why

`apps/website/content/blog/2026-08-31-what-changes-when-the-runtime-changes.mdx` concedes, accurately:

> Every AG-UI backend in our repository is itself a LangGraph graph… what our parity data
> demonstrates is a transport swap over one runtime. It is not a runtime swap.
> …Whether the neutral `Agent` contract holds up against a genuinely non-LangGraph AG-UI
> backend — CrewAI, Mastra, Pydantic AI, something you wrote — is untested by us.
> I believe it holds… But belief is not measurement.

Verified 2026-08-31: there is **zero** non-LangGraph AG-UI backend code in this repo. The AWS
Strands blog post is a tutorial written against the upstream integration; we never ran it here.

That post is **paused** until this work lands.

|---|---|---|---|---|---|

**Negative cells are the valuable result.** Two are already expected to fail:

- **Interrupts** ride a `CUSTOM` event named `on_interrupt` emitted by the *LangGraph* bridge.
  It is a bridge convention, not a protocol primitive.
- **Subagents** need native `ACTIVITY_SNAPSHOT` / `ACTIVITY_DELTA`, which our demo backend
  emits deliberately.

Measuring exactly where the contract stops being neutral is worth more than five green checks.

## The blocking prerequisite

`deployments/ag-ui-dev/server.py` is **hardcoded to LangGraph**: it imports `ag_ui_langgraph`,
calls `add_langgraph_fastapi_endpoint()` per topic, and `requirements.txt` pins `langgraph` +
`ag-ui-langgraph`. Both are generated by `scripts/generate-ag-ui-deployment-config.ts` from
`apps/cockpit/scripts/capability-registry.ts`.

Nothing lands until that generator supports per-topic framework adapters and per-topic
dependencies. Lane B needs a second hosting target entirely.

## Structure

New top-level `cockpit/runtimes/<runtime>/` rather than extending `cockpit/ag-ui/`. The
existing seven are one-runtime-many-capabilities; this axis is one-capability-many-runtimes,
and mixing them would make both matrices unreadable.

Cockpit examples must remain standalone — duplicate, never share across examples.

One isolated worktree each. Read-only on this repo plus external research; each stands up a
minimal local server and reports what the generator and cockpit actually need. No repo
changes, no PRs — findings only. Implementation is planned after all three report.

## The headline

Messages, tool calls, and state work against three genuinely non-LangGraph runtimes, in two
languages, with **zero adapter changes**. The portability claim is now measured rather than
believed.

## Two adapter defects, both ours, both fixable now

**1. Interrupt detection.** `reducer.ts` keys interrupts on `CUSTOM name === 'on_interrupt'`,
an ag-ui-langgraph convention. Strands and Microsoft both use the protocol-standard
`RUN_FINISHED.outcome = {type:'interrupt', interrupts:[…]}` and emit `on_interrupt` **never**.
Our RUN_FINISHED handler ignores `outcome`, so the run finalizes `success` with a dangling
approval call and `interrupt()` stays undefined.

**Verified directly by the main session, contradicting the Strands spike's headline claim:**
`@ag-ui/core@0.0.52` does **NOT** strip `outcome` — a `RUN_FINISHED` carrying an interrupt
outcome parses cleanly with `outcome` intact. A reducer fix works today. No dependency
upgrade is required.

**2. Resume payload shape.** `to-agent.ts` sends only `{command:{resume}}` (the LangGraph
shape). Mastra requires `command.interruptEvent{toolCallId,runId}`; Microsoft wants structured
entries addressing every pending interrupt.

`RunAgentInputSchema` in 0.0.52 has **no `resume` field** (verified), so the protocol-standard
resume array is not sendable on the current pin — but `forwardedProps` **is** a field, and all
three runtimes read resume from it today. Adopting the standard array later is cleaner, not a
prerequisite.

## Subagents: red everywhere, honestly

Three different non-mappings, none of them our bug. Strands routes delegation through
`CUSTOM MultiAgentHandoff` + `STEP_*` with zero ACTIVITY events. Mastra reserves ACTIVITY for
background tasks and observational memory. Microsoft emits coarse `activityType:"executor"`
snapshots and constructs `ACTIVITY_DELTA` nowhere. Our `activityType === 'subagent'` filter is
our own demo-backend convention; no third party emits it.
